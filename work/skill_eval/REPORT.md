# iclr-submissions skill 测试报告

测试的是 `release/skills/iclr-submissions/`：一个指导 coding agent 基于 ICLR 数据回答问题的 skill。每次测试都起一个全新的 sub-agent，它只能看到 `release/` 目录，相当于一个刚 clone 了开源仓库的使用者。各次运行的答案和过程记录在本目录 `iteration-*/` 下。

## 测试设计

| 题目 | 检验的路径 |
|---|---|
| 1 2026–27 年 agent safety 论文用了哪些 environment，分布如何 | 用安全标签圈定论文集合，关键词覆盖不足时逐篇阅读（用户给的示例题） |
| 2 RLVR/GRPO 论文的 base model 变化 | 没有现成标签的话题，用正则加主题簇圈定集合，关键词计数 |
| 3 2026 年安全子方向的录用率，与 2027 年投稿热度是否一致 | 直接用标签统计和录用数据 |
| 4 2025→2027 年世界模型投稿的增长和驱动方向（第二轮新增） | 三年数据、非安全话题，检验泛化 |

第一轮中，题 1–3 各跑一次有 skill 和无 skill；无 skill 的 agent 只看 README。第二轮修改 skill 后，重跑题 2，并新增题 4。

## 结果

| 题目 | 有 skill | 无 skill | token（有/无） |
|---|---|---|---|
| 1 环境分布 | 7/7 | 6/7 | 36 万 / 15 万 |
| 2 base model（第一轮） | 6/6 | 5/6 | 16 万 / 13 万 |
| 3 录用率与热度 | 6/6 | 6/6 | 10 万 / 9 万 |
| 2 base model（第二轮） | 6/6 | — | 17 万 |
| 4 世界模型（第二轮） | 6/6 | — | 35 万 |

评分项能区分有无 skill 的只有「给出代表论文链接」：有 skill 的五次运行全部给了，无 skill 的三次都没给。主要结论的方向两组一致，例如 Qwen 份额上升、Llama 下降，agent safety 的环境重心从 Web/GUI 转向工具链。这说明底座模型本身已经很强，skill 的价值不在于「能不能答」。

## 构建者视角 vs 使用者视角

构建者知道很多数据「坑」，使用者不知道。skill 的核心作用，就是把构建者的这部分知识交给使用者。

| 构建者知道的坑 | 第一轮有没有传递到使用者 | 第二轮 |
|---|---|---|
| 2027 年总量是 2026 年的 2.17 倍，要比份额 | 有。两组都做到了 | — |
| 2027 年 42% 的摘要是模板化写法，影响词频类结论 | 有。有 skill 的每次都做了稳健性检验，并在题 1 中发现 tool/API 上升有一部分来自写法；无 skill 的只有部分做了 | 保持 |
| 关键词只能覆盖部分论文，没命中不代表没有 | 有。有 skill 的读了 377 篇摘要并给出置信区间；无 skill 的用规则分类，抽查 90 篇 | 保持 |
| 只有 2027 年有 TL;DR | **没有，而且 skill 的脚本把它带进了搜索**。无 skill 的 agent 自己发现了这一点 | 已修复：默认不搜 TL;DR，并写入数据说明 |
| 「提到」不等于「使用」（base model 可能只是对比对象） | 两组都自发做了上下文核对 | 已写入 skill，并新增 `context` 子命令 |
| 分母要选「点名了该属性的论文」：2027 年点名模型的比例本身在上升 | 两组都自发做到了 | 已写入 skill，并新增 `count --among-matched` |
| 录用率有两种分母（含不含撤稿和 desk reject） | 两组都给了两种口径 | 已写入 skill，并新增 `rate` 子命令 |
| 新子社区会造新词（"world action model"） | — | 题 4 自己发现了，已写入召回检查 |

两个视角最大的差别是：构建者的知识里有盲区（TL;DR），而且这个盲区会被固化进工具，悄悄传给所有使用者。这说明必须用全新的 agent 测试，而不能只靠构建者自己复查。

## 第二轮的改动

- 脚本修复了 TL;DR 问题，并新增或扩展了以下功能：
  - `rate`：分组录用率，带 Wilson 置信区间和两种分母；
  - `context`：按关键词查看上下文片段；
  - `count --among-matched` 和 `--exclude-formulaic`；
  - `batch --sample-per-year` 支持按年份设不同样本量，并保存抽样名单；
  - `tally --ci` 和 `--population-per10k`，后者把样本份额换算成每万篇投稿的估计值；
  - `merge` 的输出自带写作风格和状态两列；
  - `show --random`。
- SKILL.md 新增「构建者知道的坑」清单（分母、提到不等于使用、TL;DR、撤稿），以及没有 sub-agent 时的阅读方案。
- 数据说明（data.md）补充了 aggregates 的字段含义、两个同名主题簇（47 和 213）以及 TL;DR 的说明。

## 设计原则（从测试中总结）

1. **只写模型不知道的东西。** 底座模型已经会用 pandas、会想到比份额，再写这些只会稀释注意力。值得写的是数据特有的坑和构建过程中留下的信息，例如标签是怎么来的、哪些年份缺字段、写作风格的变化。
2. **把判断写成决策表，不要写成命令。** 例如「这个属性是有固定名称的东西就用关键词计数，需要判断就逐篇阅读；覆盖率低于约 80% 时，剩下的论文要读」。这让 agent 遇到新问题也能自己选路。
3. **把重复劳动沉淀成脚本。** 第一轮里，多个 agent 各自写了分组录用率、置信区间、上下文检索。第二轮把这些放进了 `iclr.py`。
4. **工具的默认值必须安全。** TL;DR 的问题说明，工具的默认行为比文档更有影响力。
5. **示例只示范过程，不给答案。** 示例写的是如何定义、如何检查覆盖率、如何设计标注规范，也写了一个真实的教训（模板化写法让 tool/API 的上升打了折扣），但没有给最终的分布数字。

## 局限

- 测试 agent 在这个环境里不能再起 sub-agent，所以「交给 sub-agent 并行逐篇阅读」这条主路径没有测到，测到的是没有 sub-agent 时的退路。用户直接在 Claude Code 里使用时，通常可以走主路径。
- 只有 4 道题，每题每种配置只跑 1 次，看不出结果的波动。评分是我按断言人工判定的。
- skill 的 description 还没有做触发率优化。
